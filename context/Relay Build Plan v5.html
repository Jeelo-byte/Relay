C · Product rules & the two-axis status model

If a feature doesn't help create, prove, update or act on an agreement, it isn't P0. Agreements are a shared-understanding view — not a legal contract, not legal advice.

Axis 1 — review_state (you vs. the AI)

ValueMeaningShown asTransitions
suggestedAI found it; you haven't looked“Suggested” section, dashed card border, sparkle icon→ accepted (Accept / Edit+Save) · → dismissed
acceptedYou confirmed it (or created it manually)Normal card→ dismissed only via Delete (writes tombstone)
dismissedYou said “not an agreement”Hidden; listed in Settings › Dismissed (undo)→ suggested (Undo within list)

Axis 2 — lifecycle (the real-world agreement)

ValueMeaningChip
offeredSomeone proposed/asked; the other side hasn't clearly acceptedOffered
agreedBoth sides acceptedAgreed
fulfilledAll obligations doneDone
cancelledCalled offCancelled
disputedParties' later messages contradict each otherDisputed

Derived (never stored): Overdue = lifecycle ∈ {offered, agreed} ∧ an open obligation's due end < now. Due soon = due within 48 h. Waiting on you = an open obligation where obligor is self. Waiting on them = obligee is self, obligor is someone else.

Rules every agent enforces

  • The AI never changes an accepted agreement. It appends a timeline event with review_state:"suggested"; the user applies or rejects it. The AI may revise its own still-suggested agreement (logged in timeline).
  • No term without evidence. Every amount, date, place and party on an AI agreement cites ≥1 evidence item. Missing = “Not stated”.
  • Totals count only accepted, open obligations with a stated amount, grouped per currency, never converted. Derived amounts (split bills) count only after the user accepts them.
  • Manual mode is complete: create, edit, delete, mark done with zero LLM calls.
  • Only opted-in rooms the user is in are read. Opt-in defaults to off for every room.
  • Nothing is shared with other participants. No auto-send, ever.
  • Dismissed is sticky: event IDs covered by a dismissed suggestion are never re-suggested unless a new message changes them.

E · Crypto spec (exact)

Every parameter is fixed. Swift and TS must produce byte-identical output for the test vectors in packages/crypto-vectors.json.

E1 · Key hierarchy

passphrase  ──NFKC normalise (no trim)──► UTF-8 bytes
salt        = 16 random bytes (stored clear in Neon)
master      = Argon2id(passphrase, salt, opslimit=3, memlimit=64 MiB, out=32)   // libsodium crypto_pwhash ALG_ARGON2ID13
KEK         = HKDF-SHA256(ikm=master, salt="", info="relay/v1/kek",  L=32)
auth_key    = HKDF-SHA256(ikm=master, salt="", info="relay/v1/auth", L=32)  // sent to server at login
verifier    = SHA-256(auth_key)                                          // server stores this only

DEK         = 32 random bytes per account per key_version
blob_key    = HKDF(DEK, info="relay/v1/blob")
db_key      = HKDF(DEK, info="relay/v1/sqlcipher")
lease_key   = HKDF(DEK, info="relay/v1/lease-hmac")
token_key   = HKDF(DEK, info="relay/v1/local-secrets")   // wraps Matrix access token on web

recovery_secret = 39 random Crockford base32 chars (195 bits) + 1 Crockford mod-37 check char
                  → shown as 8 groups of 5 (e.g. 7KQ2M-…); input normalised: uppercase, O→0, I/L→1, spaces/dashes removed
recovery_KEK    = HKDF(ikm = UTF-8 of the 39 data chars, info="relay/v1/recovery-kek")   // no Argon2: high-entropy

E2 · Wrapping

wrapped_dek = AES-256-GCM(key=KEK | recovery_KEK, nonce=12 random,
                          aad="relay/v1/wrap|{account_id}|{key_version}|{wrap_type}",
                          plaintext=DEK)
stored as: nonce(12) || ciphertext(32) || tag(16)

E3 · Blob envelope

plaintext_json → UTF-8 → pad: append 0x80 then 0x00… to the next bucket
  buckets: 512, 1K, 2K, 4K, 8K, 16K, 32K, 64K
nonce = 12 random bytes (never reused; ~2^32 blob limit per DEK is far above need)
aad   = "relay/v1/blob|{account_id}|{row_id}|{version}|{key_version}"
ct    = AES-256-GCM(blob_key, nonce, aad, padded)
envelope (bytes) = 0x01 (format) || key_version (uint32 BE) || nonce(12) || ct||tag
transport: base64url (no padding) in JSON
  • version in AAD = the version the client is writing (base_version + 1). Server can't move a blob to another row, account or version without the tag failing.
  • Rollback: client stores HighWater[row_id] = max version seen; any pulled blob with lower version is ignored and logged as a sync issue.
  • Decrypt failure: quarantine the row (keep ciphertext, don't overwrite), increment Settings › Sync issues counter, continue.

E5 · Flows

  1. Sign-up: choose handle (3–32 chars [a-z0-9_], not an email — client rejects “@”) + passphrase (≥ 12 chars, zxcvbn score ≥ 3) → derive → generate DEK + recovery secret → wraps → POST /v1/accounts → show recovery code → user retypes groups 2 and 7 → continue.
  2. Login new device: GET /v1/prelogin?handle → salt+params → derive → POST /v1/sessions with auth_key → receives wraps → unwrap DEK with KEK → store per E4.
  3. Recovery: enter code → recovery_KEK unwraps recovery wrap → force new passphrase → re-wrap DEK with new KEK + new verifier → PUT /v1/accounts/credentials.
  4. Passphrase change: needs old auth_key; re-wrap DEK only (no blob re-encryption).
  5. Rotation (v1, manual): new DEK (key_version+1) → re-encrypt all blobs locally → upload → new wraps → delete old wraps. Old key kept in memory until done. Devices seeing an unknown key_version prompt for passphrase.
  6. Device removal: revoke session server-side; the removed device can still read what it already downloaded — UI says so and offers “Rotate keys”.
Unrecoverable by design — shown at sign-up and on the recovery-code screen: “If you lose your passphrase, all your devices, and this recovery code, nobody — including us — can recover your agreements.”

H4 · Dedupe, change detection, completion

  • Same window twice: any overlap between new evidence event IDs and an existing agreement's covered_event_ids with same obligor+obligee → treat as update of that agreement.
  • Same room, different words: same obligor/obligee pair, same kind, amounts equal (or both null), due within ±2 days → merge into existing as an update suggestion.
  • Cross-room / cross-network: never auto-merge. Set flags.possible_duplicate_of → UI “Looks like the same as …” with Merge / Keep both.
  • Change: field-by-field diff of normalised values → one timeline event per changed field (term_change_suggested, pending:true) → banner on card “Maya changed the date to Monday — Apply / Ignore”.
  • Completion: “sent”, “paid”, “done”, Venmo/CashApp/Zelle mention, “got it thanks” → complete op → pill “Mark as done?” (never auto-done). paid_text with a smaller amount → payment_partial timeline event; remaining = amount − paid shown, obligation stays open.
  • Cancellation: “nvm”, “never mind”, “can't anymore”, “cancel” → cancel suggestion.
  • Dispute: two parties assert contradicting values in later messages → lifecycle=disputed suggestion with both quotes.

  5. covered_event_ids: union.

J3 · Extraction leases (fixes A5)

lease_key = HMAC-SHA256(lease_key, room_id + "|" + last_event_id_in_window)    // server sees 32 opaque bytes
priority  = Mac 4 · iPad (Tier A) 3 · iPhone 2 · Web 1
wait      = Mac 0 s · iPad 10 s · iPhone 45 s · Web 90 s  (after the window trigger, before acquiring)
acquire(ttl 180 s) → granted → run pipeline → push blob → complete
                   → not granted, held → mark messages "leased"; when the holder's blob arrives the
                     covered_event_ids remove them; if TTL passes with no blob → retry acquire
                   → state done → skip

The keyed HMAC is deterministic for your devices but unguessable for Neon (it doesn't have the key), so it doesn't break the “no deterministic IDs linkable to messages” rule. It leaks only “two devices processed the same window”.

J4 · Messages plane vs derived plane

  • Messages: Matrix only. Each device syncs Matrix itself. Never in Neon.
  • Derived (agreements, settings, dismiss markers, device info): Neon ciphertext.
  • Web: IndexedDB stores {row_id, version, envelope} only plus an encrypted Matrix sync cache (envelopes under token_key); plaintext lives in memory. One tab is sync leader (Web Locks API); others listen on BroadcastChannel. Lock state shared across tabs.
